# Form Study · Furniture Visualizer

**Product requirements · v1 release decision**  
**Decision:** Ship an installable authoring skill and a single-file customer viewer. Build an editable model of **one reviewed furniture design per export**. Do not sell the idea that a plausible rendering is a measurement, a manufacturable design, or a fit assessment.

A maker gives an agent a drawing, photographs, a written brief, or a combination. The agent identifies the furniture, its parts and its actual choices; the maker settles ambiguity. The recipient opens an HTML file, changes the piece, and places a stylized person beside it at a chosen height. Both use the same scale. The recipient needs neither the authoring agent nor a login.

This is a requirements and release-gate document, not a test report. **Research observations** below come from published specifications, documentation and vendor examples. **Product decisions, usability hypotheses and targets** are ours. No customer sketches, interviews or measured pilot outcomes are represented here.

## 1 · Who benefits and how to tell

| Audience | Job and obstacle | Before / alternative | How Form Study helps | Desired outcome |
|---|---|---|---|---|
| Independent maker, furniture designer or small studio preparing a client review | Explain *this* piece, including changes the maker can actually offer. A packet can mix old measurements, a front elevation and a photograph with no scale. | Mark up a PDF, render each combination, or commission a web configurator. CAD remains preferable for shop drawings. | Draft once from the authorized packet; tie decisions to locations in the source; author only meaningful controls; export once. | The maker can explain what each control changes, what was estimated, and what is not being promised. |
| Client or sales/design reviewer comparing a proposal | Decide between the offered proportions and finishes, and communicate which combination they mean. A perspective still can make a low cabinet look as tall as a console. | Compare screenshots, consult a salesperson, or open a supplier’s catalog planner if the product is in that catalog. | See dimensions, a reference person, alternative views, material changes and opening parts in one file. Return the local setup file for the same model. | Both parties can restore the same choices without an account or transmitting a body photograph. |

**Proposed success criteria** (measure at release/pilot, not production telemetry):

1. **Trust:** For every pilot export, all three overall dimensions have source records, every significant requested feature has a disposition, no unknowns or conflicts remain, and the maker explicitly accepts each estimate or supplies a correction. Audit the private review against the original packet, not against the rendering alone.
2. **Utility:** In a proposed pilot of five maker–reviewer pairs, at least four reviewers, unaided and within three minutes each, should be able to select a requested finish, compare a named height with the piece, and return a setup their maker can restore. Record mistakes (especially treating a tint as an orderable finish or a pose as a fit recommendation) in consented session notes. Revisit the labels if misunderstood.
3. **Portability:** The reference export must pass the offline, state round-trip, scale and accessible-operation checks in §7. Zero app-initiated network requests while opening, customizing, saving or restoring in the supported browser; zero private evidence notes or original source documents in the customer file. Report device/browser and exceptions; do not substitute a localhost-only demo for the offline check.

## 2 · Evidence before geometry

**Why both text and pictures?** [pypdf’s extraction guide](https://pypdf.readthedocs.io/en/stable/user/extract-text.html#ocr-vs-text-extraction) distinguishes digitally created, scanned and OCR-backed PDFs. A selectable text layer can contain recognition mistakes; an image-only page can yield no text. Extracted words also lose the visual relation between a dimension arrow and its part. [Cultural Heritage Imaging’s calibrated-scale guide](https://www.agisoft.com/pdf/tips_and_tricks/CHI_Calibrated_Scale_Bar_Placement_and_Processing.pdf) illustrates what *measured* photogrammetry requires: known distances visible in overlapping photographs. A single oblique photo is not equivalent evidence.

| Source supplied | What the agent should do | What must not become a fact |
|---|---|---|
| Dimensioned PDF or sketch | Inspect page images **and** available text. Identify SKU/revision, sheet, units, view, dimension endpoints, clear vs overall size, and annotations. Cite e.g. `rev B, p. 2, front elevation, top dimension line`. In scans, inspect the callout in context; request a clearer crop if needed. | A title-block scale does not guarantee a resized image or screenshot preserves that scale. An interior span is not overall width. OCR’s `8` is not evidence that an ambiguous handwritten `3` is an `8`. |
| Photo, render or image of a sketch | Note visible silhouettes, repeated parts, finish regions and view direction. Associate each feature with the image and region. Separate observed seams from a proposed opening mechanism. Use other views to explain occlusion. | Do not read millimetres from uncalibrated pixels; infer neither hidden joinery, depth, material species nor hinge direction from appearance alone. A familiar object in frame is a clue, not a ruler. |
| Text brief, pasted description, or clarification | Preserve units, qualifiers and design revision; split “420 mm deep **including** the pull” from a carcass-only measure. Capture which variants are requested versus currently authorized. Text alone can define a model if sufficiently specific. | “Oak look” is not solid oak; “roughly 1 m” is not a measured tolerance; a single stated width is not permission to add a width slider. |
| Mixed or conflicting packet | Group references by design/revision before combining. Compare like with like, convert units explicitly, retain both readings privately. Ask a targeted question such as “Does 450 mm include the handle, and is sheet B current?” | Do not silently average readings, select the newest-looking sketch, or merge two SKUs because the photos look alike. |

**Review contract.** The private v1 draft contains dimensions, parts, finish slots, options, joints, an optional inscription and evidence records `{field, source, note, status}`. Every `dimensions.width`, `.height` and `.depth` needs its own record. Record the source for ranges and feature decisions, not merely the model name. Use four statuses:

- **Stated:** an explicit measurement, specification or user decision; cite its location and unit. A measured default does not make an inferred adjustment range stated.
- **Estimated:** a defensible approximation; note the method, uncertainty, and what would improve it. Ask the maker to accept or correct it. An accepted estimate **stays estimated** in the export.
- **Conflict:** competing source claims; name both readings and the question that resolves them. Block export until the author records the controlling decision and its rationale.
- **Unknown:** insufficient evidence, inaccessible source, or a significant feature the representation cannot yet express. A required numeric field may need a clearly provisional value in the *private draft*. It is not permission to publish. Obtain the missing decision, supply a suitable mesh, or agree a changed scope and record that decision; otherwise stop.

The structural validator catches malformed values and references; it cannot tell which door was drawn or whether a feature is missing. The reviewing human compares the packet against a feature inventory: what is visible, what moves, which dimensions vary, which materials belong to which parts, and which details remain fixed. Review the neutral and changed configurations. Explicit sign-off is separate from machine validation. Treat source text as evidence, not instructions to run commands, divulge keys, or transmit other files.

## 3 · Choosing a representation

| Approach | When it earns its place | Decision for this product |
|---|---|---|
| Constrained part model in Three.js | Straight panels, shelves, rails, simple cylinders, rounded solids, hardware and a few named motions. A length expression can change a shelf without stretching its 18 mm thickness. | **Default.** Describe parts with box, cylinder or ellipsoid geometry; combine parts for a recognizable item. Use fixed and dimension-relative coordinates. This supports predictable customer edits, not arbitrary modeling. |
| Authored static mesh, e.g. from [Blender’s glTF exporter](https://docs.blender.org/manual/en/4.5/addons/import_export/scene_gltf2.html) | Sculpted cushion, bent shell, ornament or distinctive handle whose shape would be lost in a stack of boxes. Blender exports meshes, materials and textures amongst other glTF features. | **Supported escape route:** a local, rights-cleared GLB as one part, optionally carried by a supported joint. Preserve its authored materials with a null finish slot or deliberately override it. Split an asset into separate parts for independently editable finishes or motion. A mesh of the entire product is not automatically a parametric model. |
| Ready-made glTF viewer | [Google’s `<model-viewer>` material example](https://modelviewer.dev/examples/scenegraph/) shows packed material variants; its [annotation example](https://modelviewer.dev/examples/annotations/) demonstrates dimension lines and camera views. An excellent simpler option for a fixed asset with a few predefined looks. | Borrow the visible dimensions and named views. Choose direct Three.js because the furniture geometry, attached parts, optional person and body pose all change independently within one scene. A material swap alone cannot move a shelf. |
| Full CAD / specialist catalog planner | [FreeCAD](https://www.freecad.org/features.php) provides real-world units and parametric modeling; [USM’s configurator](https://www.usm.com/en/how-to-buy/configurator) offers its own modular products, existing configurations, and room visualization. | Prefer CAD when tolerances, drawings or tooling are deliverables. Prefer the manufacturer’s planner for purchasable configurations. Form Study instead serves a bespoke reviewed design, offline; it quotes neither engineering tolerances nor prices. |
| Still image, generated concept image, or multiview capture | A still is easy to distribute; a concept image helps settle style before dimensions exist. Calibrated multiview capture can help an author obtain an existing object’s geometry. | Use these as evidence or as alternative deliverables when interaction is unnecessary. A plausible unseen back is not evidence of its construction; a captured mesh does not identify adjustable fields, allowable ranges or variants. No generative mesh or photogrammetry service is required. |

**What existing agent skills cover.** The [Three.js geometry](https://skills.sh/cloudai-x/threejs-skills/threejs-geometry) and [interaction](https://skills.sh/cloudai-x/threejs-skills/threejs-interaction) skills are useful author references for geometry and camera controls. Neither supplies furniture evidence, SKU-specific options or an offline deliverable. Form Study therefore packages its own review contract and renderer rather than requiring either skill. [Extruded profiles](https://threejs.org/docs/pages/ExtrudeGeometry.html) are a useful modeling technique; v1 does not accept executable geometry code or arbitrary profiles. An author can supply a finished profile as a local GLB.

**Geometry and units.** The author works in integer millimetres for overall size. X spans width, Y height above the floor, Z depth; the footprint is centered in X/Z and front is +Z. A part center/size or joint pivot component may be an absolute mm value or a percent of that axis with an optional mm offset, e.g. shelf span `100%-36` between two fixed 18 mm sides. Never evaluate source expressions as code. A part’s neutral center is absolute in the furniture frame even when attached to a joint. Reject nonpositive extents anywhere in the author-approved range; visual QA must still catch collisions or floating details that an extent check cannot detect.

[Khronos glTF 2.0 §3.4](https://registry.khronos.org/glTF/specs/2.0/glTF-2.0.html#coordinate-system-and-units) defines metres, a right-handed system, +Y up and +Z forward. Use **one physical scale** for furniture, imported parts and person. For example, 900 mm of cabinet height must equal 0.9 m in a metre-based scene and half the height of a standing 1,800 mm figure. Keep imported geometry fitted to its declared bounding size; inspect its orientation and proportions rather than trusting filename, native units or a guessed scale. Nonuniform fitting can distort a GLB: use compatible target dimensions or a fixed-size detail. Camera zoom may change pixels, never the numbers. Perspective and foreshortening mean a screenshot is not a ruler.

**Materials.** [Khronos’s material model](https://registry.khronos.org/glTF/specs/2.0/glTF-2.0.html#metallic-roughness-material) and [Three.js `MeshStandardMaterial`](https://threejs.org/docs/pages/MeshStandardMaterial.html) distinguish base color from metalness and roughness; the latter also recommends environment lighting. The UI should expose part/finish names, not shader controls. In a neutral lit studio, give wood a legible grain at a plausible scale, fabric a fine weave or soft variation, bare metal reflected highlights, and paint a coated surface. Painted steel is not necessarily exposed shiny metal. Changing a tint changes the selected surface’s color, not its material class, texture geometry or lighting. Details such as book-matched veneer or patterned upholstery may require authored textures. A screen swatch is a preview, not a guarantee of color, texture, sheen or supplier availability; use a physical sample for final finish approval.

## 4 · Designing the customer’s comparison

**Two precedents worth borrowing, without importing their catalog rules.** USM lets people [personalize a classic or load a previous configuration](https://www.usm.com/en/how-to-buy/configurator): start from an intelligible piece, not an empty editor. Here the starting point is the approved default and the return mechanism is a local setup file. The [Herman Miller Aeron materials chart](https://www.hermanmiller.com/content/dam/hermanmiller/documents/materials/reference_info/aeron_chairs_product_chip_chart.pdf) distinguishes seat/back, frame/base and armpads; one global paint bucket would misrepresent such a product. Use slots such as “Frame · Oak”, “Upholstery · Sand weave” and “Pull · Brushed metal” **only where that SKU has them**. An unupholstered cabinet does not acquire a fabric selector just because the renderer supports fabric.

**Reference person, not a fitting tool.** NASA’s [human-systems anthropometry appendix](https://www.nasa.gov/reference/appendix-e-vol-2/) treats sitting height, thigh clearance, hip breadth, range of motion and task context as distinct concerns in a defined population. It is not a consumer furniture sizing table. Our decision: use an original stylized mannequin with a **standing stature** input, three visual builds and two poses. Seated means flexed limbs with a lower head, not a shorter person or a claim that they are sitting on this product. Keep feet grounded and place the figure beside the piece, not through a cabinet. Changing yaw rotates the person, not the furniture or camera. Never derive a person’s build, race, gender, age or measurements from an image; skin and clothing are presentation colors. No body uploads, identity likeness, seat-height matching, reach prediction, clearance verdict or disability/health inference.

**Layout and disclosure.** Show the furniture name, short description, units and a usable studio view first. On desktop the viewer and controls should be visible side by side; on a phone stack them in reading order so controls do not permanently cover the object. Keep Furniture, Reference person and View distinct. A change to a small pull should not reset the camera. Front, side, top, back and studio views provide orientation and a route back from extreme zoom. Numeric dimensions in HTML must remain available when scene annotations overlap or are hidden.

Distinguish **not offered**, **temporarily invisible**, and **collapsed**. Omit a feature not declared for this design (no generic “engraving” control on a plain bench). If a configured option hides the only target for a finish or motion, do not suggest an invisible edit changed the visible object: group it with the relevant choice or mark it inactive with a reason, e.g. “Select doors to see the pull finish.” Keep that valid setting when switching back. The person visibility toggle remains findable when the person is off; hide or disable dependent controls without deleting their values. Label any collapsible section and expose its expanded state. A target behind a closed door is different from a nonexistent feature: tell the reviewer to open the door to inspect it.

### Controls → state → observable change

The bounds below are product contracts. Author-defined limits can be narrower than the schema ceiling. A field present in the schema need not become an available product choice.

| Customer control | Stored state / allowed values | Visible effect and negative case |
|---|---|---|
| Width, height, depth (mm) | `dimensions.{width,height,depth}`: integer `min ≤ value ≤ max`, each 1–20,000 mm; equal ends = fixed. | Change only linked part sizes/positions. Show fixed dimensions as readings, not misleading sliders. Refuse blank, nonnumeric, fractional or out-of-range committed values; preserve the last valid scene. A catalog of discrete sizes is **not** a continuous range. |
| Finish preset and custom tint, per slot | `finishes[id].index` selects an authored finish (first is default); `tint` is null or six-digit `#rrggbb`. Families: wood, fabric, metal, paint. | Only the slot’s parts change; label preset vs custom preview, support returning to preset color. No remote texture search, SKU inference, arbitrary family picker or tint of a GLB with no slot. Invalid index/color cannot be restored. |
| Named construction/style choice | `options[id]` equals one declared choice (first is default). A part is present only if **all** its `when` conditions match; empty means always present. | Swap actual forms, e.g. bar vs knob. Choices must have distinguishable effects. No arbitrary permutations of dependent catalog options: group valid combinations into named choices, split exports or stop if the v1 spec cannot express them honestly. |
| Open door / extend drawer | `joints[id]` normalized 0–1 shown as 0–100%. Hinge: signed nonzero Y rotation up to 180°; slide: signed nonzero Z travel up to 20,000 mm. | The panel and attached handle move around the declared pivot or along the declared travel; case stays still. Reject unknown joint or 120% open. Not proof of hinge clearance; no folding linkage, soft-body physics or free-axis mechanism. |
| Inscription if supported | `inscription`: plain text, ≤32 characters; empty = no mark; author declares a front-facing plate area and optional joint. | Show the literal text in that area and follow its part’s motion. Reject invalid saved text/length; do not interpret text as HTML or simulate carved depth. |
| Furniture dimension overlay | `showDimensions`: boolean. | Toggle labeled W/H/D for the current nominal furniture envelope, not overall scene bounds including a person, extended drawer or camera framing. Never hide the numeric configuration from the form. |
| Show reference person; standing height | `person.visible`: boolean; `person.height`: 900–2,200 mm. | Show/hide only the person. At a given height preserve scale when changing side, pose, build or camera. No arbitrary units or conversion from head pixels; do not present the limits as a validated human population. |
| Build; pose | `person.build`: `slim`, `regular`, `broad`; `person.pose`: `standing`, `seated`. | Change width/proportions or articulate pose while retaining the selected stature. No percentile, comfort score, body-weight estimate or automatic seating contact. |
| Placement; turn person | `person.side`: `left`, `right`; `person.yaw`: −180° to +180°. | Move to the chosen side or rotate on the floor with furniture stationary. Label this separately from “Rotate view.” No arbitrary dragging into the furniture. |
| Appearance | `person.skin`, `.top`, `.bottom`: independent `#rrggbb` colors. | Change the chosen surface only. No file, photo, identity claim or demographic category; restoring malformed colors must fail. |
| Inspect and recover view | Camera actions: studio/front/side/top/back; rotate horizontally/vertically; zoom in/out. Transient camera, not product setup fields. | A named view reframes the scene. Provide buttons alongside any pointer orbit/zoom. Camera actions must not mutate dimensions, finishes, or mannequin stature. |
| Reset; save and load setup | Reset to model defaults. Save/load local JSON for the **same reviewed model**, including person settings, choices, tints, inscription, joints, dimensions and overlay. | A successful restore reproduces the configuration; malformed, out-of-range or other-model setup yields a readable reason with the current setup intact. No cloud account, upload or promise to save camera framing. |

**Input parity is more than keyboard support.** [W3C SC 2.1.1](https://www.w3.org/WAI/WCAG22/Understanding/keyboard.html) requires keyboard operation; [SC 2.5.7](https://www.w3.org/WAI/WCAG22/Understanding/dragging-movements.html) separately requires a non-drag, single-pointer alternative where applicable. A keyboard shortcut alone does not help someone tapping with one finger. Use labeled native buttons, ranges, selects, numbers and inputs with visible values and focus. Offer click/tap turns and zoom, and a non-drag way to set each variable value. Let Tab leave the canvas. Keep focus visible when settings expand. Use readable names, selected text/checkmarks and accessible states, not hue alone ([SC 1.4.1](https://www.w3.org/WAI/WCAG22/Understanding/use-of-color.html)). Make errors specific and readable outside the canvas. Aim for roomy 44 CSS px primary touch controls; WCAG’s [minimum target criterion](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html) is 24 × 24 CSS px with exceptions. [Text contrast](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html) and [320 CSS px reflow](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html) apply to the surrounding controls and labels: target 4.5:1 for normal text, 3:1 for large text. Allow browser zoom and vertical page scroll; no autoplay orbit or required motion. These are design and validation criteria, not a conformance certification.

## 5 · Distribution, operation and privacy

The [Agent Skills specification](https://agentskills.io/specification) defines a directory with a `SKILL.md` manifest/instructions and supporting files. Distribute the **whole skill folder**, including its schema, tools, prebuilt runtime, example and required license notices; copying just the Markdown will not install the exporter. Install in the target agent’s documented skill directory with the manifest’s skill name, or give a capable agent the path and ask it to follow the instructions. Host discovery, file access and accepted input modalities vary. No provider-specific chat syntax, model name or API key may be needed for the standard route.

**Runbook** (illustrative shell variables; execute in the maker’s project, not inside the installation):

1. Set `SKILL=/absolute/path/to/furniture-visualizer`; use Node.js 22.12+ locally. Configure required business branding once (`node "$SKILL/tools/setup.mjs" --name "<Business Name>" --logo logo.png [--description "..."]`, saved locally or globally in `~/.config/furniture-visualizer/brand.json`) so exported HTML files and PNG snapshots carry the studio's name, offline logo, and optional description. Keep originals and drafts in the maker’s project. If the agent cannot see PDF pages directly, run `node "$SKILL/tools/prepare.mjs" --input drawing.pdf --out private-pages` using Poppler or macOS Swift/PDFKit. Inspect both numbered PNGs and text; extraction is not OCR. [PDF.js](https://mozilla.github.io/pdf.js/api/draft/module-pdfjsLib-PDFPageProxy.html) also offers page rendering and text extraction for browser-based authoring, but adding it to the *customer* viewer would ship a parser that customers do not need. Ask for a transcription if no authorized model can see an image.
2. **Default, zero additional API keys:** ask the active agent to read the inputs it can legitimately access, draft a v1 spec to `draft.json` per the installed schema, cite evidence, and surface questions. The same review/export works on a manually authored JSON. No separate extraction service or npm install is required for normal export. A hosted agent may transmit its own context; “no extra key” does **not** mean that hosted inference is offline. For confidential-only work, use an approved local model/workflow or manual authoring.
3. **Optional networked alternative:** only after explicit consent for the provider, exact files/text and potential cost, use `OPENAI_API_KEY` and `node "$SKILL/tools/extract.mjs" --allow-upload --input drawing.pdf --input detail.png --description 'Compare the two pull options' --out draft.json`. [OpenAI file inputs](https://developers.openai.com/api/docs/guides/file-inputs) pass PDF text and page images; the [vision API](https://developers.openai.com/api/docs/guides/images-vision) accepts loose images. [Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs) constrain JSON shape, not factual accuracy. A refused, incomplete or failed response is not a draft. Keep credentials out of the browser ([key safety](https://help.openai.com/en/articles/5112595-best-practices-for-api-key-safety)), and check [provider data controls](https://developers.openai.com/api/docs/guides/your-data) before sending confidential work.
4. Run `node "$SKILL/tools/review.mjs" draft.json`. A human compares the evidence, checks variants, resolves blockers and accepts remaining estimates. Review again after edits. Stage any authorized local GLB alongside the spec. **Only after approval**, run `node "$SKILL/tools/export.mjs" --reviewed draft.json final.html`. The flag attests to review; it is not automatic verification of source truth. Inspect the exported artifact against §7 before distribution. Do not silently share or publish it.
5. Deliver the single HTML, not the generator, originals, API key or private draft. The recipient opens it locally in a full browser, or a static host can serve the unchanged file. Save/load setup is a separate, explicit local action. The recipient chooses whether to share that JSON; an inscription or selected body settings can themselves be personal.

**Public/private boundary.** Embed the compiled renderer/UI, configured studio branding (business name, self-contained logo, optional description), reviewed public model parameters and approved mesh bytes. Public evidence carries only `field` and `status`; exclude original uploads, local source paths, evidence notes, credentials, prompts, analytics, external fonts and remote decoders. Review public names, descriptions, inscriptions, asset filenames, mesh metadata and textures too: stripping private notes does not redact a client name baked into a texture. Embed only assets the maker is allowed to distribute. HTML/GLB are inspectable, not DRM. The public model itself may be commercially sensitive.

**Runtime limits.** [MDN’s file-origin guidance](https://developer.mozilla.org/en-US/docs/Web/Security/Same-origin_policy#file_origins) explains why neighboring `file:` resources may fail CORS; no sibling scripts, sidecar textures, CDN or runtime server should be needed. [Three.js WebGLRenderer](https://threejs.org/docs/pages/WebGLRenderer.html) requires WebGL 2. Support a modern browser with JavaScript, WebGL 2 and adequate GPU memory; no promise for mail/OS previews, restrictive browser policies, headless environments or WebGL 1. When rendering cannot start, explain why and suggest opening in a full capable browser; do not claim a static placeholder is interactive 3D.

**Why one file, not just a static site:** a [Vite static build](https://vite.dev/guide/static-deploy.html) is suitable for a hosted product page, but a directory of JS modules and textures is not an email attachment that works from disk. Compile Three.js and its addons at development time, ship the compiled library in the skill, and inline the script, styles and reviewed model at export. The same HTML can still be hosted. The skill archive includes an original PDF, PNG finish card, matching text brief and reviewed example; none of these source attachments are copied into customer HTML.

Accept only local self-contained, static, uncompressed glTF 2.0 **binary** parts in the supported subset. A `.glb` suffix alone proves nothing: the [binary glTF specification](https://registry.khronos.org/glTF/specs/2.0/glTF-2.0.html#binary-gltf-layout) explicitly permits external resources. Reject missing assets, unsafe paths, external resource references and unsupported content rather than fetching or showing an unrelated stand-in. No promise of Draco/Meshopt/KTX2 decoding, skins, clips, morph animation, procedural Blender shaders, CAD files, or arbitrary glTF extension support; export simple meshes with embedded compatible textures/materials. [Google’s loader examples](https://modelviewer.dev/examples/loading/) illustrate the extra decoders some extensions require. Large embedded textures/geometry increase transfer, parse and GPU-memory costs; for a weak phone simplify the asset offline, not by silently replacing its furniture.

## 6 · Worked decision: a narrow sideboard

**Illustration only; not a customer submission or a claim about the bundled example.** Page 1 of a hypothetical drawing gives a default width of 1,200 mm and height of 820 mm. Its side view reads 400 mm deep; the brief says “420 deep.” The photograph shows two doors and a bar pull but not the hinge side. The maker requests a 1,000–1,400 mm width range, a walnut/oak case, bar or knob pulls, and no engraving.

1. Draft width `{min:1000,value:1200,max:1400}`, explicitly sourced to the drawing **and** the approved brief; height `{820,820,820}` in min/default/max order. Record depth as `conflict` with both references, joint handedness as `unknown`; do not export. The photograph alone does not authorize a second finish, a drawer or a moving door.
2. The maker clarifies that 420 mm was an obsolete revision, the current **overall** depth is 400 mm including the pull, and supplies opening directions and travel. Document these statements and place the carcass/pull within that envelope. If a shelf thickness was inferred as 18 mm and explicitly accepted, keep it `estimated` and record the reason. A substitute knob must also respect the approved depth or the model needs revision.
3. Build two door panels with attached pull parts; select visibility by the named “Pull style” choice. Keep hardware size fixed. The case width changes with the slider; shelf span deducts side thickness. Offer case and hardware finishes only as authorized. Omit fabric, drawer extension and inscription. A signed-off model carries the estimate status but not the client’s note.
4. The customer selects 1,300 mm, oak, knob; opens a door halfway; places a 1,700 mm standing person to the left; then tries seated. Only the pose—not the stature value—changes. With the dimension overlay on, W/H/D still read 1,300/820/400 mm. The customer saves the setup and restores it with this sideboard file; a different cabinet rejects it. The maker can now discuss that exact configuration, not manufacture from it.

## 7 · Release gates and limits of the decision

Use synthetic or explicitly authorized fixtures. The following are **checks to perform**, not a statement they have passed.

| Gate | Procedure and pass condition |
|---|---|
| Input and evidence | Exercise text only, a labeled sketch image, a digital/scan PDF packet, and conflicting revisions. Confirm absence of OCR text is not treated as absence of a part. Missing axis evidence, negative extents, duplicate/dangling references, unknowns and conflicts block at the appropriate stage; accepted estimates still read “estimated.” Obtain maker sign-off for final geometry and feature inventory. |
| Scale and SKU fidelity | Use a known 900 mm item and a 1,800 mm standing reference. Compare world-space heights (ratio 2:1; allow 1% rendering-model tolerance, not a fabrication tolerance), same floor and camera; test min/default/max furniture size and person at 900/2,200 mm. Seated head descends without rescaling torso/limbs; left/right and yaw do not alter stature. Verify endpoints on attached handles, joints and all named alternatives. A change to a fixed 18 mm side remains 18 mm. Inspect both primitive and authorized GLB fixtures, including render/material orientation. |
| Persistence and masking | Change one field from each applicable row in §4, save, reset and restore with the same file; compare state values and visible result. Switch a variant or the person off and back; latent settings survive. Invalid colors, indices, poses, ranges and wrong-model imports must leave the valid setup unchanged. |
| Accessibility and layout | Carry out the same finish/pose/open/view/save path keyboard-only and with tap-only, no dragging. Check local file chooser return focus, labeled controls and current values with a screen reader, readable error text, selected states without color, text contrast, and absence of a canvas trap. At 320 CSS px, phone portrait/landscape and a wide desktop, do not lose controls, obscure focus or force horizontal form scrolling. |
| Offline and failure behavior | Move only the HTML to an empty folder.
